# 08 自回归推理与 KV Cache

上一章用 GQA 减少了 KV 头的数量，但还没有回答另一个问题：生成第二个、第三个新 Token 时，为什么还要计算那些已经处理过的位置？KV Cache 的思路是保存每层历史位置的 Key 与 Value，让新增 Query 直接读取它们。它改变的是重复计算和状态管理方式，不改变我们希望得到的模型结果。

本章使用一个两层的 RoPE + GQA Decoder，在同一组随机权重、同一批 Token 上比较完整重算、单步增量和分块增量。模型没有训练，实验也不评价生成能力。我们要建立的是可执行的不变量：在明确的数值容差内，每个位置的 logits、每层 hidden，以及最终的 KV 状态都应一致。

## 学习目标与先修

需要先理解第 02 章的因果注意力、第 03 章的完整 GPT 计算、第 06 章的 RoPE，以及第 07 章的 KV 头共享。完成后，你应能独立解释并检查：

- Prefill 与 Decode 各自消费什么输入、产生什么 logits 和缓存。
- 为什么历史 K/V 可以复用，而新增 Token 仍需要经过所有网络层。
- RoPE 的位置偏移与非方形因果掩码为什么必须一起处理。
- 两层网络为什么需要分别维护两份 KV，而不能只缓存输入 embedding。
- 缓存形状合法为什么仍可能属于错误请求，以及何时必须丢弃缓存。
- 理论缓存容量、实际缓存张量字节数与进程峰值内存有什么区别。

本章范围是 CPU、FP64、等长且没有 padding 的批次、连续追加的缓存。不实现左右 padding、不同长度的连续批处理、分页缓存、滑动窗口淘汰、量化缓存、跨设备调度或分布式推理。它们会改变状态管理与掩码要求，应当在基础一致性建立后单独研究。

## 1. 一个输出位置到底预测什么

设已知输入是 $x_0,\ldots,x_{P-1}$。完整模型输出形状为 `[B,P,V]`，其中位置 $i$ 的 logits 用于预测 $x_{i+1}$。因此，提示词 Prefill 后最后一个位置的 logits，已经可以用来选择第一个新 Token；不需要先把这个未知 Token 送入模型。

选择得到 $x_P$ 后，下一次 Decode 才把 $x_P$ 输入模型，更新缓存到长度 $P+1$，并取得预测 $x_{P+1}$ 的 logits。常见的对齐错误，是把“本次产生的 Token”和“本次已经写进缓存的 Token”当成同一个东西。采样只是根据 logits 选择 ID；缓存只会在 Token 真正经过网络时增长。

```text
Prefill 输入：x[0:P]      → 缓存覆盖 0...P-1 → 最后 logits 预测 x[P]
采样：       得到 x[P]    → 此时缓存仍只到 P-1
Decode 输入：x[P:P+1]    → 缓存覆盖 0...P   → logits 预测 x[P+1]
```

实验没有让随机模型自由生成文本，而是给出固定的整段 ID 序列，再按不同分块方式送入。这让我们能够逐位置对齐结果，隔离缓存正确性；它相当于已知后续 Token 的计算对照，不能解释为模型成功预测了这些 Token。

## 2. 为什么历史中间状态可以复用

因果 Decoder 的位置 $i$ 只依赖输入前缀 $x_{0:i}$。对于同一模型、同一前缀、同一位置规则，当你在末尾追加位置 $i+1$ 时，历史位置在第一层的输出不会改变；下一层历史位置的输入也不会改变。逐层递推，每一层历史位置的 K/V 都保持不变，因此可以保存下来供新增位置读取。

这个论证依赖因果性和一致的计算条件。若某一层允许历史位置看见未来，追加新 Token 就会改变历史 hidden，旧缓存随即失效。若切换了权重、适配器、位置编码规则、精度约定或模型模式，也不能直接沿用旧缓存。训练时的 dropout 和梯度图管理还会带来额外问题；本章只讨论 `eval()` 与推理模式下的缓存。

为什么通常保存 K/V 而不是 Q？历史 Query 的输出已经计算完毕，新增位置使用的是自己的 Query，并不会再次以历史 Query 发起读取。K/V 则仍是新增位置的读取对象。保存所有层历史 hidden 当然也可能减少部分重算，但会占用另一套状态，并且没有直接提供注意力所需的 K/V。本章采用通常的每层 K/V 形式。

逐位置的 RMSNorm、FFN 和残差都只需要处理新增位置；因果注意力需要读取历史 Key/Value。缓存没有让新 Token 跳过网络，也没有消除注意力对上下文长度的依赖。

## 3. Prefill 与 Decode 的形状

设批量为 $B$，已缓存长度为 $P$，本次输入块长度为 $C$，Query 头数为 $H_q$，KV 头数为 $H_{kv}$，每头维度为 $d_h$。进入某一层时，新块 hidden 为 `[B,C,D]`。

| 张量 | 形状 | 是否保留到后续调用 |
| --- | --- | --- |
| 新 Query | `[B,Hq,C,dh]` | 否 |
| 新 Key / Value | 各 `[B,Hkv,C,dh]` | 是 |
| 历史 Key / Value | 各 `[B,Hkv,P,dh]` | 是 |
| 拼接后的 Key / Value | 各 `[B,Hkv,P+C,dh]` | 是 |
| 注意力分数 | `[B,Hq,C,P+C]` | 否 |
| 本次层输出 | `[B,C,D]` | 下一层消费 |

Prefill 是 $P=0$ 的特殊情况，一次处理完整提示。单 Token Decode 是 $C=1$ 的特殊情况。分块输入则允许 $C>1$，既要看全部缓存，又要在块内保持因果性。

对 GQA，保存的缓存沿用 $H_{kv}$ 个头，不应为了匹配 Query 的头数而把展开后的 K/V 当作长期缓存。实验在计算注意力时使用 `repeat_interleave` 展开，以便直接阅读和验证，但写入缓存的仍是未展开的张量。高效分组内核可进一步避免展开产生的临时副本，这属于实现效率问题。

## 4. RoPE 必须使用完整序列中的位置

RoPE 将每对特征按位置相关角度旋转。采用相邻偶奇维配对，对于位置 $p$ 与频率 $\omega_r$：

$$
\begin{pmatrix}q'_{p,2r}\\q'_{p,2r+1}\end{pmatrix}
=
\begin{pmatrix}\cos(p\omega_r)&-\sin(p\omega_r)\\
\sin(p\omega_r)&\cos(p\omega_r)\end{pmatrix}
\begin{pmatrix}q_{p,2r}\\q_{p,2r+1}\end{pmatrix}.
$$

K 使用同样的位置规则。本章频率为 $\omega_r=10000^{-2r/d_h}$。已有 $P$ 个位置时，新块应使用 `arange(P, P+C)`，不是 `arange(C)`。缓存中的 Key 已经按它原来的绝对位置旋转，拼接时不能再整体旋转一次；Value 在这个实现中不应用 RoPE。

```python
past = 0 if previous is None else previous[0].shape[2]
positions = torch.arange(past, past + count)
q, k = rope(q, positions), rope(k, positions)
if previous is not None:
    k = torch.cat((previous[0], k), dim=2)
    v = torch.cat((previous[1], v), dim=2)
```

如果每次 Decode 都把新 Query、Key 位置重置成零，形状仍正确，计算也可能全部有限，但与历史位置的相对旋转关系已经错误。尤其不要把“RoPE 关注相对位置”误解为“每个块可以单独从零编号”。相对关系是由两端一致的坐标体系共同产生的。

如果移动一个完整前缀时，所有相关位置统一平移，在某些 RoPE 定义下可以推导注意力分数的不变关系；这与只重置新块、保留旧 Key 的位置完全不同。长上下文缩放、窗口重定位等策略还可能改变频率或状态更新，必须依据具体实现重新验证。

## 5. 非方形因果掩码如何构造

完整前向的分数矩阵是 `[T,T]`，可以使用下三角。增量输入的分数矩阵是 `[C,P+C]`。新块的局部 Query 下标 $i$ 对应绝对位置 $P+i$，Key 下标 $j$ 已经是拼接后的绝对位置，所以允许关系为：

$$
\operatorname{allowed}(i,j)=[j\le P+i],\quad
0\le i<C,\quad 0\le j<P+C.
$$

若 $P=3,C=2$，正确的允许矩阵是：

```text
            Key: 0 1 2 3 4
Query 位置3      1 1 1 1 0
Query 位置4      1 1 1 1 1
```

直接写 `ones(C,P+C).tril()` 得到的却是：

```text
Query 局部0     1 0 0 0 0
Query 局部1     1 1 0 0 0
```

它把左上角当成坐标原点，让新增 Query 读取不了大部分历史与当前位置。这个错误未必出现 NaN，因为每行仍有允许元素；只检查有限值无法发现它。

正确实现是显式比较绝对位置：

```python
allowed = torch.arange(past + count)[None, :] <= (
    past + torch.arange(count)[:, None]
)
scores = scores.masked_fill(~allowed[None, None], -torch.inf)
probabilities = scores.softmax(-1)
```

单 Token Decode 中，唯一 Query 的绝对位置就是当前最后位置；所有已缓存和当前 Key 都应可见。此时不需要再阻止任何未来 Key，因为缓存里根本没有未来位置。分块输入才需要阻止块内尚未到达的位置。使用 SDPA 或其他库接口时，要核对其非方形 `is_causal` 对齐语义，不能将接口名称当作这个偏移公式的替代品。

## 6. 两层网络的缓存应怎样组织

实验结构为：Token embedding → 两个 pre-norm Block → RMSNorm →词表投影。每个 Block 包含 RoPE + GQA 注意力、残差和 SwiGLU FFN。宽度为 24，4 个 Query 头、2 个 KV 头、每头 6 维；头维度为偶数以支持所用 RoPE 配对。模型共 11,976 个参数，没有训练。

```text
cache = [
    (layer_0_rotated_keys, layer_0_values),
    (layer_1_rotated_keys, layer_1_values),
]
```

第二层 K/V 来自第二层的输入，即第一层新增位置完成注意力与 FFN 后的 hidden。它们不是第一层 K/V 的复制，也不能由最初 embedding 直接代替。因此，对照实验除了最终 logits，还逐层比较 hidden 与最终缓存：如果第一层已正确、第二层开始偏离，就能更快定位到逐层状态或残差路径。

本章用函数输入、输出显式传递缓存，没有把它保存在全局变量中。`cache=None` 表示新请求；调用返回一个新列表和拼接后的张量。`torch.cat` 不原地修改传入缓存，这便于验证旧前缀不变，但也意味着每次追加都会分配与复制，不能当作生产系统的最优缓存方案。

模型检查每层缓存数量、K/V 形状、批量、头数、维度、dtype、device 和共同长度，并限制总长度不超过 64。这个上限是教学接口的边界，不是证明模型能有效理解长度 64 的文本。结构检查也没有能力确认某个形状合法的缓存究竟属于哪段提示；请求归属必须由上层调用者管理。

## 7. 从零运行独立实验

完整源码在 [experiments/08-kv-cache/main.py](https://github.com/zhanghuiwan/llm-architecture-lab/blob/main/experiments/08-kv-cache/main.py)。脚本不导入其他章节，不下载数据或权重，只依赖标准库与 PyTorch；安装方式见[实验指南](/labs)。在仓库根目录运行：

```bash
.venv/bin/python experiments/08-kv-cache/main.py --quick
.venv/bin/python experiments/08-kv-cache/main.py
.venv/bin/python experiments/08-kv-cache/main.py --quick --seed 7
.venv/bin/python experiments/08-kv-cache/main.py --quick --output experiment-results/cache.json
```

快速模式使用批量 2、长度 13、首段长度 3；单步方案按 `[3,1,1,...]` 输入，分块方案按 `[4,3,1,5]` 输入。常规模式改为批量 3、长度 19、首段长度 5，分块为 `[6,2,4,1,6]`。两种方案都拼接每次输出，得到与完整前向相同顺序的 `[B,T,V]`。

检查不是只比最后一个 Token：

1. 对齐所有位置的完整、单步与分块 logits。
2. 对齐两个 Block 各自的全部 hidden。
3. 对齐最终每层旋转后的 K 与未旋转的 V。
4. 验证显式零长度缓存与 `None` 等价。
5. 验证带偏移的两 Token 块，并确认传入缓存没有被原地改变、追加前缀逐项相同。
6. 核对缓存头数、各层状态、有限值与字节预算。
7. 修改未来 Token，确认过去 logits 不变。
8. 故意重置位置或使用错误左上角 mask，确认数值对照能发现它们。
9. 故意带入旧请求缓存，观察输出改变；丢弃后恢复新请求结果。
10. 检查错误批量、不同层长度、缺失层、空输入和超出接口容量都被拒绝。

脚本标准输出是一个 JSON 对象；`--output` 写入相同内容。`checks` 是实际执行的 33 项布尔检查，任何失败都会抛出错误并非零退出；`metrics.maximum_absolute_errors` 保留正确分支的逐项误差，错误实现的差异单独报告，不与正常误差混成一个数。

## 8. 实际结果如何解读

在 CPU、PyTorch 2.8.0+cpu、FP64、seed 42 的快速运行中，33 项检查通过。单步 logits 与完整前向的最大绝对差约为 $6.66\times10^{-16}$，分块 logits 约为 $5.55\times10^{-16}$。常规模式全部通过，逐层 hidden 的最大差约为 $1.33\times10^{-15}$。这些是浮点求和顺序产生的数值量级，不要求逐 bit 相等。

对照检查使用 `atol=1e-10, rtol=1e-9`。不能把 FP64 容差原样用于 FP16/BF16，低精度需先建立误差分布，再选择合理容差。本章没有执行低精度或 GPU 路径，也不比较推理速度。

错误位置分支的快速 logits 最大差约 0.0853，错误三角 mask 约 0.6515；两者均远高于数值容差，因此被负向对照发现。这样的反例证明检查能识别两种具体错误，不证明它能发现所有缓存错误。

seed 7 的快速运行也通过全部检查，正确 logits 差约为 $6.66\times10^{-16}$。随机权重有助于暴露维度与状态错误，但不同种子仍不是形式化证明。建议扩展更多前缀长度和块切分，而不是只复制这一个成功样本。

## 9. 缓存容量：先说明统计对象

若有 $L$ 层，缓存使用每元素 $s$ 字节的 dtype，当前缓存长度为 $T$，则 K 与 V 的总逻辑容量为：

$$
M_{KV}=2LBH_{kv}Td_hs.
$$

因子 2 来自 Key 和 Value。本章快速配置为 $L=2,B=2,H_{kv}=2,T=13,d_h=6,s=8$，因此：

$$
M_{KV}=2\times2\times2\times2\times13\times6\times8=9984\text{ bytes}.
$$

实验通过 `sum(t.numel()*t.element_size())` 逐张量统计最终缓存，实际恰为 9,984 字节。若仅把保存头数改成 4 个，其余预算项不变，则对应容量是 19,968 字节，GQA 的逻辑缓存预算为其一半。这是头数维度的容量对照，不是将当前 GQA 权重无损变成某个独立训练 MHA 的证明。

这份统计没有计入模型权重、注意力分数、展开的 K/V、Python 容器、分配器保留空间，也没有计入为了实验对照而同时保留的完整、单步与分块缓存。它不是整个 Python 进程的内存，更不是峰值内存。常规配置的最终缓存统计为 21,888 字节，变化来自批量和长度，而非模型学到了更多内容。

连续 `cat` 还可能在拼接时同时保留旧、新张量；显式展开会产生临时计算对象。因此，逻辑容量降低不保证同等比例的峰值内存下降。要讨论生产显存，需使用真实内核、分配方案与测量工具。

## 10. 计算节省与仍然存在的代价

无缓存逐 Token 生成时，长度不断增长的完整前缀被反复送入所有层，历史位置的投影、FFN 与注意力都重新计算。有缓存后，Prefill 做一次，随后每步只为新增 Token 计算投影和 FFN，但这个 Query 仍读取越来越长的 K/V。

忽略常数和层数，完整前缀长度 $t$ 的投影与 FFN 通常有 $O(tD^2)$ 项，稠密注意力有 $O(t^2D)$ 项。缓存后的单步计算约有 $O(D^2+tD)$ 项，但总缓存随上下文长度线性增长。长上下文和小批量时，读取 KV 的带宽、内核调用与调度可能成为瓶颈。

不要仅凭渐近式给出某台机器上的加速倍数。本章为清楚起见使用 Python 控制流、`cat` 和 KV 展开，数值正确并不意味着实现高效。下一章会讨论预热、同步、计时范围与对照内核；在此之前，只能说缓存减少了哪些重复计算。

## 11. 缓存的生命周期与请求归属

缓存是带语义的状态：它属于具体模型、具体前缀、具体批次顺序与位置策略。即使形状、dtype、device 都合法，将请求 A 的缓存用于请求 B，也会让 B 的 Query 读取 A 的历史内容。实验将同一小段后缀分别作为全新请求、以及带旧前缀的续写输入，快速运行中的 logits 最大差约为 0.524；这两种输入的条件概率本就不同。

正确的新请求使用 `cache=None`。清空后，输出与真正的独立前向再次一致。真实服务应明确请求 ID、有效长度、已写入位置、容量、批次重排映射与所有权。缓存池中的一块内存“可以重新分配”，不代表其中已有数据“可以继续作为有效上下文”。

前缀复用需要更严格的条件：实际 Token 前缀、模型权重和位置规则一致，并且只能复用对应的有效范围。提示词内容看上去相似，或解码后的字符串相同，都不足以证明 Token 序列与内部状态相同。本章不实现前缀哈希或跨请求共享。

当输入超过容量时，实验直接报错。简单丢掉最老的 KV 也不是自动正确的通用办法：模型的可见上下文和位置解释都可能改变。若采用局部注意力或滑动窗口，应该定义窗口语义，再与一个对应的非缓存参考计算逐位置比较。

## 常见错误与定位顺序

| 表现 | 优先检查 | 本章对应证据 |
| --- | --- | --- |
| Prefill 一致、第一次 Decode 就不同 | 新块 RoPE 偏移和非方形 mask | 两种故意错误均被数值对照发现 |
| 第一层一致、第二层开始不同 | 是否为每层保存各自 K/V，层索引是否错位 | 逐层 hidden 与 KV 对照 |
| 单步一致、分块不同 | 块内未来遮挡、拼接顺序和块边界 | 不同块切分与两 Token 偏移检查 |
| 同一后缀偶尔结果异常 | 是否带入旧请求状态、批次是否重新排序 | stale cache 与 reset 对照 |
| 数值一致但内存超预算 | 是否长期保存展开后的 KV、旧张量或计算图 | 逻辑字节统计与范围说明 |
| 只生成文本不同而 logits 未检查 | 先比较同一输入每个位置 logits，再研究采样随机性 | 本章不以自由生成作为验收 |

排查时先关闭随机采样和 dropout，固定权重与输入，在较高精度下比较最早偏离的位置和层。不要先放宽容差，也不要通过改 Prompt 让两个文本“看起来更像”。

## 练习与提示

1. **改变块切分。** 将长度 13 的分块改为 `[1,1,2,3,6]`，再构造几个随机正整数切分。提示：切分之和必须等于输入长度，每次返回的 logits 顺序不能改变。
2. **手算偏移 mask。** 写出 $P=4,C=3$ 的允许矩阵，并解释最后一行为什么全部允许。提示：不要从局部下标直接画三角，先写 Query 绝对位置。
3. **验证重复旋转错误。** 在一个实验分支中对缓存 Key 再次应用 RoPE，观察最早偏离层与位置。提示：保持正确分支不动，使用单独负向对照，不能把错误结果变成新的参考。
4. **改变 KV 头数。** 分别取 1、2、4 个 KV 头，重新验证每种模型内部的完整与增量一致性，并计算容量。提示：不同头数的随机模型不应互相比 logits；比较的是各自实现内部的一致性。
5. **研究 FP32 误差。** 将模型和空缓存 dtype 一起改成 FP32，记录不同长度下的误差，再提出容差。提示：不要只把阈值扩大到“能通过”，先保留逐层最大误差，并运行负向对照确保仍可检出。
6. **设计 padding 扩展。** 先画出批内两条不同长度提示的物理位置、逻辑位置和允许 mask，再考虑代码。提示：不能仅凭共享 `past=cache.shape[2]` 表示每条样本的有效长度；本章的接口需要扩展。
7. **避免每步 cat。** 设计预分配缓存与写入下标，再与本章参考实现比较。提示：应区分容量和已用长度，读取未写区域必须被阻止；性能测量放到正确性验证之后。

## 完成本章的标准

你应能从输入位置推导 RoPE 偏移和允许矩阵，运行完整／单步／分块三种计算，解释逐层对照与负向对照的意义，核对缓存字节数，并明确新请求何时必须清空状态。完成这些之后，再进入性能测量，才有可靠的语义基线。
