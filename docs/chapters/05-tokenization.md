# 05 Tokenizer 与数据管线

网络接收的是整数序列，而读者看到的是文字。Tokenizer 把这两个世界连接起来：它决定一个整数代表一个字节、一段文本，还是一个只能由应用插入的控制标记。接下来，数据管线决定这些整数如何被切块、组合、对齐为输入和标签。即使注意力和优化器都实现正确，这一层的错误也足以让架构比较失去意义。

本章不依赖上一章的模型对象。我们用 Python 标准库从零实现一个小型 byte BPE，随后建立文档隔离的 packing 数据结构。实验不训练语言模型、不下载词表或语料，重点是让每个数据转换都有可以检查的不变量。完成后，你应该能判断：一个压缩率变化来自什么；哪些位置应该计算 next-token loss；EOS、attention mask 和 loss mask 分别负责什么。

## 5.1 学习目标与先修知识

需要熟悉 Python 的列表、字典与 UTF-8 编码，理解第 01 章中输入与标签错开一位的关系。若还没有读注意力章节，也可以完成编码实验；在解释文档隔离矩阵时，再回看因果掩码的定义。

本章结束时，应当能独立完成下面的工作：

- 根据训练语料统计相邻 token 对，按确定的顺序构建并应用合并规则。
- 区分 Unicode 字符、UTF-8 字节、BPE token 与特殊 ID，解释它们为什么不是同一种单位。
- 证明普通文本可以往返还原，并证明普通文本不能直接插入内部特殊 ID。
- 在拟合 tokenizer 之前划分文档，保存划分和合并规则，固定比较中的数据配方。
- 构建定长输入、移位标签、位置编号以及同文档因果 attention，检查尾块和跨文档边界。

实验源码：[experiments/05-tokenization/main.py](https://github.com/zhanghuiwan/llm-architecture-lab/blob/main/experiments/05-tokenization/main.py)。它是本章完整可运行实现；下面的片段用于讲解，不需要手工拼接成另一个版本。

## 5.2 先分清四种计数单位

Python 中 `len("模型")` 是 2，因为它有两个 Unicode 码点；`len("模型".encode("utf-8"))` 是 6，因为这两个汉字各占三个 UTF-8 字节。视觉上一个 emoji 也可能由多个码点和修饰符组成。例如带肤色和职业标记的 emoji 并不一定对应一个 Python 字符，更不一定对应一个模型 token。

字符级模型直接给字符编号，便于教学，但有限词表需要处理未见字符。字节级模型把基础 ID 固定为 0 到 255；任何 UTF-8 文本都能先编码成这些字节，不需要给陌生汉字增加一个 `<unk>`。代价是中文、emoji 等文本初始序列更长。Byte BPE 从这 256 个基础单位出发，把常见相邻片段合并成新的单位，在覆盖能力与序列长度之间折中。

本实验的 `pieces` 字典将普通 token ID 映射到 `bytes`，而不是映射到“可显示字符”。一个 piece 可能只是某个汉字的前两个字节，它单独不是合法 UTF-8，但与后续 piece 拼接后可以还原原文。因此解码必须先连接所有字节，再整体执行严格 UTF-8 解码。逐个 token 调用 `decode(errors="replace")` 会把中间片段替换为乱码，这种损坏无法靠后续拼接补救。

需要保持的往返关系是：

$$
\operatorname{decode}(\operatorname{encode}(s))=s.
$$

它针对的是这个实现接受的 Python 文本和无归一化策略，不是在承诺可以把任意非法 UTF-8 字节解释为文本。若生产系统做了 NFC、大小写、空白或其他归一化，往返对象应改为明确的规范化文本，并且保留这种差异的说明。

## 5.3 Byte BPE 怎样学习合并规则

设一个文档当前为 token 序列 $z=(z_0,\ldots,z_{n-1})$。BPE 的一步训练是：统计全部训练文档内部的相邻对，选择最频繁的一对 $(a,b)$，分配新的 ID $c$，把所有不重叠的相邻 $(a,b)$ 替换成 $c$。新的 piece 为两个旧 piece 的字节连接：

$$
\operatorname{piece}(c)=\operatorname{piece}(a)\Vert\operatorname{piece}(b).
$$

循环执行后得到一个有顺序的规则表。这里的顺序是模型的一部分，不是可以随意重新排序的集合。每一步统计的是上一次合并后的序列；训练第十步时看到的 token 对，可能包含第九步才建立的 ID。

### 频次相同也必须给出确定答案

本实验使用以下选择键：

```python
left, right = min(counts, key=lambda pair: (-counts[pair], pair))
```

首先按频次降序；频次一样时按两个 token ID 的字典序升序。因此对 `"abab"` 与 `"cdcd"` 训练一步时，`(97, 98)` 和 `(99, 100)` 都出现两次，前者被选中，产生 ID 259。再编码 `"ababc"`，结果应当是 `[259, 259, 99]`。脚本对这个小例子有精确断言，避免只做“运行两次结果一样”的自我比较。

这不是说所有 tokenizer 都必须采用同一种 tie-break，而是同一实验必须固定自己的选择规则。只依赖字典首次插入顺序时，交换文档顺序就可能改变词表。即使使用同一份语料，两个预处理进程的读取顺序不同，也可能得到不同的模型输入。

### 重叠出现不能同时合并

对于 `[a, a, a]`，相邻统计会看到两次 `(a,a)`，但实际替换应当从左到右扫描，得到 `[new, a]`，不能把同一个中间元素使用两次。`replace_pair` 每次匹配后跳过两个元素，否则前进一个元素。脚本对这个边界情况有专门检查。

这也解释了为什么“本次相邻对计数”不总等于“本次序列长度下降量”：重叠出现会让二者不同。不需要为了让两个指标相等而修改计数定义，但必须使用固定的统计和替换规则。

### 文档之间不统计相邻对

训练实现先把每个文档分别编码成字节列表，然后在每个列表内做 `zip(seq, seq[1:])`。它不会把上一文档的最后一个字节和下一文档的第一个字节组成待合并对。否则你会把文件拼接顺序也拟合进词表，甚至学习到原文从未出现过的跨文档片段。

本实验在最高对频次小于 2 时提前结束；同时提供最大合并次数预算。它没有工业级的增量统计、并行训练、预分词和词表剪枝。训练会反复扫描序列，适合看清算法，不适合直接处理 TB 级语料。实现简单不代表算法语义可以含糊；恰好相反，小实现更容易把语义检查完整。

## 5.4 编码、解码与特殊标记的安全边界

编码不是再次寻找“当前词表里最长的字符串”。本实现从 UTF-8 字节开始，按训练时的顺序依次执行合并。只有遵循同一个规则表与顺序，训练和推理才会看到一致的 ID。合并规则可以递归组合出较长片段，ID 本身却不包含可依赖的语言学含义。

本实验预留三个不属于文本字节的特殊 ID：

| ID | 名称 | 含义 |
| --- | --- | --- |
| 256 | PAD | 定长块中的填充，不产生训练目标 |
| 257 | BOS | 由数据管线插入的文档起点 |
| 258 | EOS | 由数据管线插入的文档终点 |
| 259 起 | 合并 token | 训练规则生成的普通字节片段 |

`encode(text)` 从不扫描 `<|eos|>` 这样的字符串来插入 258。用户真的输入这些字符时，它们只是普通文本；应用若希望结束一个文档，应当在整数序列层显式添加 EOS。这种分层避免了“用户写出某个字符串，就获得内部控制标记”的意外行为。它不等同于解决所有提示注入问题，而是收紧 tokenizer 自己的接口语义。

`decode` 默认拒绝特殊 ID，要求调用方明确传入 `skip_special=True` 才会跳过它们。这个选择可以让误传 PAD/BOS/EOS 尽早暴露，而不是静默吞掉信息。生产 tokenizer 也可以采用把特殊 ID 渲染成字符串的策略，关键是不要把两种模式混成一个不明确的默认行为。

字节覆盖不代表任意 ID 序列都一定能解码。模型自由生成的片段组合可能对应不合法的 UTF-8，脚本的严格解码会报错。本实验只验证真实文本编码后的往返；若把它接到生成模型，需要另行规定如何处理未完成的多字节字符、非法序列与流式输出，不能把 `errors="ignore"` 当作无损的修复。

## 5.5 文档划分必须先于 tokenizer 拟合

读入语料之后，先确定训练、验证和测试文档，再训练 tokenizer。不能先在全部文本上建立词表，之后才把模型训练样本切成两部分。即使 tokenizer 没有标签，它仍然根据文本频次选择了表示方式；验证集信息已经参与预处理拟合。

脚本内置八个短文档，用局部的 `random.Random(seed)` 打乱，前六个为训练文档，剩余两个再加一句固定留出文本作为验证文档。这里随机数只用于划分，不用于合并选择。保存 seed 能重现这份小样本划分；实际项目还应该保存每个文档的稳定 ID、来源、版本及内容哈希，不能指望 seed 在变化的文件列表上指向同一批数据。

留出句子含有 `~~`，而训练文本没有字节 `~`。因此新增合并 piece 不应出现该字节。脚本检查这个事实，也检查训练与验证文本集合不相交。这是为了让一个可观测的“验证内容未进入合并训练”条件存在；它不能取代对真实数据血缘的审核，也不是对近重复泄漏的完整检测。

在正式实验中，完全相同的长文档、不同网站转载的同一文章、代码仓库的近重复文件，可能在简单随机划分后落在不同集合。通常需要按来源、时间、用户、仓库或去重簇进行分组划分。对于长文档，应该先分配文档，再在各自集合内部切块，避免同一文章相邻段落同时出现在训练与验证中。

数据清洗和 tokenizer 选择也有拟合过程。不要依据最终测试集的压缩率反复调整词表大小，不要在看到测试结果后更改空白规则却仍把它称作一次未接触过的评估。架构对照开始之后，tokenizer、数据版本、处理规则与目标计算方式应一并冻结。

## 5.6 从多个文档得到固定长度训练块

只把 token 列表拼起来还不够。需要明确：模型可以读取哪段历史；哪些位置需要预测；哪些位置只是为了组成批次而填充。三个问题分别由 attention、labels/loss mask 和 PAD 表达，不能互相替代。

脚本先把每个内容序列包装为 `[BOS, ...content, EOS]`，再为每个 token 附加文档编号和文档内位置：

```text
(token_id, document_id, position_in_document)
```

将这些三元组顺序连接后，以 `block_size=11` 切成块。每个块都有长度为 11 的 `input_ids`、`labels`、`segment`、`position_ids`，以及一个 $11\times11$ 的 `attention_allowed` 矩阵。脚本还用单个短文档建立独立填充夹具，保证任何数据划分都实际检查到 PAD；正文指标表只统计三个文档的主打包结果。最后不足 11 的部分添加 PAD，`segment=-1`，对应标签为 `-100`。这里 `-100` 采用 PyTorch 交叉熵常见的忽略标签约定，但本章不调用损失函数；真正接入模型时必须保持 `ignore_index` 一致。

### 标签必须预测下一个 token

对于同一文档内部的位置 $t$，标签应为原始流中下一个 token；文档最后一个内容 token 预测 EOS，EOS 本身不预测下一个文档的 BOS。若一个文档内容有 $n$ 个 BPE token，那么这个文档贡献 $n+1$ 个有效预测目标：BOS 预测第一个内容 token，随后逐个预测，直到最后一个内容 token 预测 EOS。

因此本章数据集的有效目标总数必须满足：

$$
N_{\mathrm{target}}=\sum_{d=1}^{D}(n_d+1).
$$

脚本另外构造 `[...content, EOS, IGNORE]` 作为每个文档的目标参考，再逐项比较 packing 结果，避免只有数量正确、标签内容却错位的情况。若你对整个拼接流无条件右移，会多得到 $D-1$ 个跨文档目标。脚本把这种错误数量当成负对照，验证它确实与文档隔离配方不同。

一个输入块末尾的位置仍然可以预测原始流的下一个 token，即使那个 token 不作为本块输入出现。预测目标本来就是模型尚未读取的内容，因此这不构成未来信息泄漏。块边界会截断可见历史；这与文档边界不同，也与跨块持久化 KV cache 的训练配方不同。

### EOS 不会自动隔离注意力

即使标签已屏蔽 EOS 到下一文档 BOS，后一个文档的内容仍可能读取前一个文档的隐藏状态。因果掩码只禁止未来，并不禁止过去的另一个文档。若需要独立文档，允许矩阵必须同时满足：

$$
A_{ij}=\mathbf{1}[j\leq i]\;\mathbf{1}[d_i=d_j]\;\mathbf{1}[d_i\geq0].
$$

这里 $d_i$ 为块内位置 $i$ 的文档编号，PAD 的编号为 $-1$。每个有效 token 至少可以读取自己；不同文档之间一律不可读；PAD 的查询行与被读取列都不参与有效 attention。脚本保存的是 `True=允许` 的布尔元数据，不是可以不加检查就传给任意 attention API 的掩码。某些 API 的布尔语义正好相反；接入时应当用小矩阵核对其文档。

PAD 查询行全部为 False，适合描述语义，却可能让手写 `softmax([-inf,...,-inf])` 产生 NaN。实际模型需要安全处理全屏蔽查询行，并确保 PAD 输出与梯度不进入损失。不要因为标签忽略了 PAD 就允许中间张量出现 NaN；某些运算仍可能传播它。本章不运行 attention，因此不把元数据正确性宣称为所有后端的数值正确性。

### position_ids 的边界也需要规定

脚本采用文档内递增、遇到 BOS 归零的位置编号。一个文档跨越两个训练块时，位置继续沿用文档内编号；但模型的可见上下文只包含当前块。接入具有有限位置表的模型时，不能直接使用可能超出表长的编号，必须改为块内编号或采用与位置机制兼容的明确策略。

RoPE、绝对位置嵌入、滑动窗口和缓存各有不同的约束。相同的 token 内容、不同的 position_ids，也可能得到不同输出；它们应该跟 attention 规则一起作为数据配方记录，而不是藏在模型默认参数里。

## 5.7 独立运行实验

在仓库根目录执行。脚本只使用 Python 标准库，不需要安装 tokenizer 库或下载模型。以下使用 Python 3.12 的 `python3` 命令；如果你已进入全书虚拟环境，可改用该环境的 `python`。

```bash
python3 experiments/05-tokenization/main.py --quick
python3 experiments/05-tokenization/main.py
python3 experiments/05-tokenization/main.py --quick --seed 7
python3 experiments/05-tokenization/main.py --quick --output /tmp/ch05-result.json
```

`--quick` 使用 32 次合并预算，常规模式使用 64 次；两者都做完整的正确性检查，区别是拟合规模。`--seed` 控制划分；`--output` 可选写出与标准输出相同的 JSON 对象，父目录会创建。JSON 中的 `checks` 是本次实际执行的布尔检查，失败时脚本抛出异常并非零退出，不会输出一个仍写着成功的报告。`metrics` 保存压缩和 packing 数据，没有伪造的训练 loss 或吞吐量。

脚本不读取仓库文件，因此从别的工作目录也能运行，只需把脚本路径写成绝对路径。这一点使每章真正可以独立执行，避免依赖前一章生成过词表、训练过模型或留下临时文件。

### 一次实际运行应该怎样解读

本实现使用 seed 42，已实际运行快速与常规两种模式。两种模式的 27 项检查均通过，得到：

| 指标 | 快速模式 | 常规模式 |
| --- | --- | --- |
| 训练／验证文档 | 6／3 | 6／3 |
| 合并次数 | 32 | 64 |
| 含特殊 ID 的词表大小 | 291 | 323 |
| 训练 UTF-8 字节数 | 279 | 279 |
| 训练 token 数 | 181 | 117 |
| 训练 bytes/token | 约 1.541 | 约 2.385 |
| 验证 UTF-8 字节数 | 113 | 113 |
| 验证 token 数 | 94 | 70 |
| 验证 bytes/token | 约 1.202 | 约 1.614 |
| packing 有效目标数 | 28 | 21 |
| packing 填充数 | 2 | 9 |

packing 使用的是单独的三个小文档，不是六篇训练文档；目标数随合并规则改变，是因为同一文本被表示为不同数量的 BPE token。快速模式换为 seed 7 后，也实际通过 27 项检查，但训练 token 数变为 170，验证 token 数变为 88。这个变化来自训练文档划分改变，不能当作随机种子让算法产生了“不稳定的 tie-break”。同一划分内重复拟合、反转训练文档顺序的检查都应保持规则一致。

这些数字只是脚本内置微型语料的实际结果，不代表中文语料的一般压缩率。常规模式的词表更大、序列更短；它既没有训练语言模型，也没有测得吞吐，因此不能推导“更大的词表更快”或“验证 token 更少所以模型更强”。

## 5.8 Tokenizer 会怎样影响架构实验

序列长度影响注意力计算与缓存，词表大小影响 embedding 和输出层参数。在权重绑定时，词表相关参数大致为 $Vd$；不绑定时还会有另一份输出投影。在相同字符长度下，较短 token 序列可能降低注意力工作量，但较大的词表又可能增加 logits 和交叉熵计算。最终取决于模型宽度、batch、输出层实现、内存布局和硬件，不能只凭压缩率判断。

相同 token 数预算也不一定意味着读过相同数量的原始文本。若 A 的平均 bytes/token 是 B 的两倍，训练同样多的 token 时，A 可能已经接触更多字节。若你同时改变结构和 tokenizer，再比较每 token loss，两个目标函数的统计单位也变了。为了把效果归因于结构，最直接的办法是在架构对照中冻结 tokenizer。

若确实研究 tokenizer 本身，可以考虑在同一原始文本上报告总负对数似然、字节归一化的 bits per byte 等指标，并说明特殊 token、归一化和边界如何计数。把自然对数换成 bit 需要除以 $\ln 2$。这仍然要求对同一评估文本、同一概率分解范围正确累计似然；不能拿两个现成的平均 token loss 直接除以平均字长，便宣称可比。

本章报告的 bytes/token 仅是编码长度统计，没有任何概率模型参与，因此它不是 bits per byte，也不是困惑度。单位的名字很相似，测量对象却不同，这是实验报告中值得明确区分的细节。

## 5.9 常见错误与排查顺序

遇到乱码，先检查是否逐 piece 解码、是否做了未记录的 Unicode 归一化、是否把特殊 ID 误当普通字节；再检查编码与解码是否使用相同规则。不要先用忽略错误模式掩盖损坏。

遇到验证结果过好，先查文档划分和去重，再查 tokenizer 是否读过验证文本、是否根据测试集挑了词表。只检查随机种子相同无法发现数据泄漏。

遇到 loss 不正常，打印一个短文档的 `input_ids`、`labels`、`segment` 和位置编号，逐项确认输入与目标错位一位、最后内容预测 EOS、EOS 不跨文档预测、PAD 标签被忽略。然后画一个小的允许矩阵，观察第二个文档是否还能读取第一个文档。只有数量统计正确，并不意味着标签和掩码对齐。

遇到尾块利用率很低，不要悄悄丢弃尾块来使统计看起来更好。可以调整打包策略、按长度分桶或允许更多文档组合，但要记录丢弃的 token 数、实际训练目标数和 attention 配方。对于精确 token 预算的架构比较，loss 的分母应是有效目标数，而不是固定块大小乘以 batch。

## 5.10 练习与验收

1. 手算 `"abab"` 与 `"cdcd"` 的第一步合并，再把文档输入顺序反转。解释为什么本实现仍选择同一对。提示：先写频次，再比较 token ID 元组。
2. 加入一个从未出现过的汉字和一个组合字符，验证 roundtrip。找出一个不能独立严格 UTF-8 解码的基础字节 piece，解释为什么这不违反整体往返。
3. 故意把 `encode` 改成识别 `<|eos|>` 字符串。哪一项检查会失败？说明应用显式插入特殊 ID 与用户文本包含同名字符的区别。完成后恢复原实现。
4. 对三个极短文档手画打包结果，列出 EOS 的 labels、PAD 的 labels，以及第二文档 BOS 对第一文档 token 的允许矩阵值。提示：EOS 与因果掩码分别只解决一个问题。
5. 比较 8、16、32、64 次合并预算，报告词表、训练和验证 token 数以及原始字节数。不要把压缩趋势写成语言模型能力趋势；尝试解释为什么验证压缩收益可能弱于训练集。
6. 设计一份正式 tokenizer 工件清单：基础字节映射、特殊 ID、合并顺序、归一化、预分词规则、训练文档版本、划分和代码版本。解释仅保存 `vocab_size` 为什么无法恢复编码行为。

验收时，不只看 27 个布尔值。你应当能用自己的话解释每个不变量保护了哪个环节；能区分 tokenizer 拟合、文本编码、样本 packing 与模型 attention；能拿一个小例子确认标签和边界。做到这些，再把同一套数据约定接入最小 GPT，后续结构实验才有一个清楚、可复现的输入基础。
