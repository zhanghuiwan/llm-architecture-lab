# 11 MoE 入门：把计算分配给不同专家

前几章讨论的 FFN 有一个共同点：每个 Token 都经过同一组参数。Mixture of Experts，简称 MoE，把一组候选 FFN 放在同一层，让路由器决定每个 Token 使用其中哪些专家。它扩大了可供模型使用的参数集合，同时限制每个 Token 执行的专家数量。但路由、数据重排、负载不均和设备通信也成为计算的一部分，不能只看专家矩阵乘法。

本章从一个可以逐项核对的小实现开始：四个路由专家、每个 Token 选择两个，以及一个总是执行的共享专家。你会实现两条相互独立的执行路径，比较输出和全部梯度，再观察容量限制、路由塌缩与一次真实的合成回归训练。这里不加载大模型，也不进行专家并行；目标是建立足够精确的局部参考，便于以后阅读真实模型。

## 学习目标与先修关系

需要理解第 03 章的逐位置 FFN、第 04 章的优化循环，以及张量索引、广播和自动求导。这里将输入展平为 `[N,D]`，其中 $N=BT$ 是当前批次中参与该层的 Token 数。若实际输入有 padding，应先明确哪些 Token 参与路由和统计；本实验没有 padding，不能直接把所有位置都当成真实 Token 的做法复制到任意数据管线。

完成后应能：

- 写清 Router、Top-k、选中权重和专家加权输出的形状。
- 说明离散选择与连续权重分别怎样影响梯度。
- 用 `index_select` 收集专家输入，用 `index_add` 把多个专家贡献还原到原位置。
- 区分请求负载、容量内接受的负载，以及被丢弃的 Token–专家分配。
- 核对总参数量、每 Token 激活参数的代理统计与实际耗时的区别。
- 解读一个小规模训练结果，并说明它没有验证什么。

## 1. 从 Dense FFN 到多个候选函数

一个不带 bias 的普通两层 FFN 可以写为：

$$
f(x)=W_{\mathrm{down}}\,\phi(W_{\mathrm{up}}x).
$$

若隐藏宽度为 $D$、中间宽度为 $F$，参数量是 $2DF$。门控 FFN 通常有另一条投影，参数计数会改变；本章为了专注分派，采用 `Linear(D,F) → tanh → Linear(F,D)`。这不是在推荐 tanh 替代现代模型中的 SwiGLU，而是选择一个光滑、便于数值对照的小专家。

现在准备 $E$ 个独立函数 $f_0,\ldots,f_{E-1}$。它们输入和输出形状相同，但参数不同。路由器根据 Token 的表示 $x_t$ 生成分数：

$$
a_t=W_r x_t+b_r,\qquad a_t\in\mathbb R^E.
$$

取分数最大的 $K$ 个专家，得到集合 $S_t$。在本章的约定中，选中分数内部做 softmax：

$$
g_{t,e}=\frac{\exp a_{t,e}}{\sum_{j\in S_t}\exp a_{t,j}},\qquad e\in S_t.
$$

每个 Token 的选中权重之和为一。没有选中的专家不进入主输出：

$$
y_t=f_{\mathrm{shared}}(x_t)+\sum_{e\in S_t}g_{t,e}f_e(x_t).
$$

共享专家没有经过这个 Top-k 选择，也没有额外门控，始终独立执行。不同论文可能采用不同的分数激活、归一化、共享专家数量或门控方式；这条公式只定义当前实验，不能根据“MoE”这个名称推断所有模型都这样计算。

## 2. Top-k 权重：看起来相近的公式也要核对

先对全部专家做 softmax，取出选中概率，再除以选中概率之和，在实数运算下与直接对选中 logits 做 softmax 等价：

$$
\frac{p_{t,e}}{\sum_{j\in S_t}p_{t,j}}
=\frac{\exp a_{t,e}}{\sum_{j\in S_t}\exp a_{t,j}}.
$$

脚本实际检查这两个结果。若取出全局概率后不重新归一化，权重之和一般小于一，输出尺度就变了。若某个模型有意使用不归一化的分数，那是另一个明确定义的设计，不能在复现时凭习惯补上归一化。

Top-k 的索引选择是离散操作。在选中集合不变的局部区域内，选中分数与权重仍能求导，所以 Router 可以从加权输出获得梯度；跨越选择边界时，集合会改变，整体函数不是处处光滑。实验检查第 $K$ 与第 $K+1$ 大分数之间没有数值并列，避免把边界行为误当成普通光滑点。

一个容易忽略的特例是 $K=1$：若只对这一个选中 logit 做 softmax，权重恒为一，主输出沿这条权重路径无法训练 Router 的分数。辅助项、不同权重定义或其他路由估计可能提供梯度，不能因此说 Top-1 路由“没有任何训练方法”。本章固定 $K=2$，不把结论外推到所有 Top-1 实现。

## 3. 先画出张量与索引

快速和常规模式的正确性部分使用相同的小配置：

| 量 | 数值 | 含义 |
| --- | --- | --- |
| $N$ | 16 | 本层接收的 Token 数 |
| $D$ | 6 | Token 表示宽度 |
| $F$ | 12 | 每个专家的中间宽度 |
| $E$ | 4 | 路由专家数量 |
| $K$ | 2 | 每个 Token 请求的专家数量 |
| 共享专家 | 1 | 每个 Token 都执行 |

输入为 `[16,6]`，Router logits 为 `[16,4]`，Top-k 索引和权重均为 `[16,2]`。专家输出仍是 `[收到的Token数,6]`。最后把加权贡献放回 `[16,6]`，再与共享专家输出相加。

这里需要两个索引，而不是只记专家编号：`token_ids` 指出原始 Token，`slots` 指出它在 Top-k 结果中的哪一槽。一个 Token 可以同时出现在两个不同专家的输入批次中，因此还原时必须累加。普通覆盖赋值会让后一个专家覆盖前一个专家，形状完全正确但结果错误。

核心路径如下，完整入口还包含统计、容量和参考实现：

```python
for expert_id, expert in enumerate(self.experts):
    token_ids, slots = (indices == expert_id).nonzero(as_tuple=True)
    selected = token_ids[:keep]
    selected_slots = slots[:keep]
    contribution = expert(x.index_select(0, selected))
    contribution *= weights[selected, selected_slots, None]
    routed = routed.index_add(0, selected, contribution)
output = self.shared(x) + routed
```

`nonzero` 在这里返回按原 Token 顺序排列的分配；`keep` 由容量决定。若没有 Token 分配给某专家，跳过这个专家的前向。空专家没有主输出梯度是合理现象，不能通过给它伪造一个训练样本来“消除空梯度”。

按专家执行减少了 Python 层逐 Token 调用次数，但它仍是教学循环，包含离散索引和动态批量，不是融合 GPU 内核。代码路径更成批，不足以证明它在任何硬件上更快。

## 4. 用另一条执行路径检查输出与梯度

如果两份“参考实现”共享同一套分派索引，某些索引错误可能同时出现在两边。本章参考路径改为逐 Token、逐选中专家执行：为每个 Token 先计算共享输出，再按选中顺序计算并累加贡献。容量接受计数也由这条循环独立维护。

两个模型由同一初始模型深拷贝而来，输入分别启用梯度。前向检查之外，用同一个非均匀探针张量构造标量目标，并加入同样的负载均衡辅助项。然后比较：

- 输入 `x` 的梯度。
- Router 权重和 bias 的梯度。
- 四个路由专家各自的 up/down 权重梯度。
- 共享专家 up/down 权重的梯度。

空梯度只在对照中按数学上的零梯度处理，不会写回优化器。实验分别检查每个参数，而不是只比较一组梯度范数；两个错误方向也可能拥有相同范数。使用 FP64 是为了使参考误差更容易解释，容差不是为低精度生产内核设定的通用阈值。

每种容量下都重复上述检查。容量为零时，主输出只剩共享路径，但本章仍将容量前的 Router 均衡项放入标量目标，因此 Router 可以从这个辅助项得到梯度。不要把这个梯度误解为被丢弃的专家仍参与了主输出。

## 5. 容量：丢掉的是一条分配还是整个 Token

“容量”必须有单位。本实验的 $C$ 表示一个专家在当前批次最多接受多少条 Token 分配，同一 Token 请求两个专家时占用两个专家各自的容量。这里按原 Token 顺序优先接受，满了就丢弃剩余分配；不随机挑选，不按权重大小重新排序。

实验覆盖三个状态：

| 容量 | 路由专家行为 | 输出含义 |
| --- | --- | --- |
| `None` | 接受全部 $NK$ 条分配 | dropless 路由加共享路径 |
| 0 | 所有路由分配被丢弃 | 只保留共享路径 |
| 1 | 每个专家最多接受一条分配 | 接受的贡献加共享路径 |

丢弃后不重新归一化剩余权重。例如某 Token 的两个请求原来权重是 0.7 与 0.3，第一个被丢弃后第二个仍乘 0.3，而不是变成 1。这一选择会改变输出尺度，正文、快路径和参考路径必须一致。真实系统也可能采用重新归一化、重路由、填充或其他策略，需要逐项核对。

应同时记录容量前 `counts`、容量内 `accepted`、按 Token 和槽标记的 `dropped`。它们满足：

$$
\sum_e\mathrm{accepted}_e+\sum_{t,s}\mathrm{dropped}_{t,s}=NK.
$$

只报告接受数量会掩盖原始负载是否极不均衡。只报告被丢弃 Token 数又会丢失细节：一个 Token 可能丢一个请求，也可能丢两个请求。在本实验中，即使两个路由请求都丢了，共享专家仍执行，所以不能说这个 Token 整层输出必为零。

一些实现从容量因子 $\alpha$ 推出 $C=\lceil\alpha NK/E\rceil$，但公式中的 $K$、舍入、最小容量、设备批次范围都可能不同。本实验直接指定整数容量，避免把一种工程约定包装成唯一标准。

## 6. 负载均衡与路由塌缩

若大多数 Token 总被送往少数专家，其他专家得不到足够训练，而忙碌专家可能造成溢出和等待。先定义统计再讨论修复。记容量前硬分配频率为：

$$
f_e=\frac{1}{NK}\sum_{t=1}^{N}\mathbb 1[e\in S_t],\qquad \sum_e f_e=1.
$$

再用 Router 对全部专家的 softmax 概率求平均，得到 $P_e$。本章采用一个教学辅助项：

$$
L_{\mathrm{bal}}=E\sum_e\operatorname{stopgrad}(f_e)P_e.
$$

当两者都是均匀分布时，这个值为 1。这个数只是均匀参考值，不是对所有可能的 $f$ 与 $P$ 都成立的全局下界。硬选择和概率可能不一致，因此不能把“接近 1”单独当成均衡或训练健康的充分证明。还应同时看每个专家的计数、概率、溢出和主任务结果。

脚本通过清零 Router 权重并设置固定 bias `[12,8,-8,-12]`，让每个 Token 都选专家 0、1。结果为 `[16,16,0,0]`，两个专家闲置，辅助项约为 2。这个负向对照证明统计能够识别一个明确的塌缩状态，不证明这个辅助项能够在任意训练任务中防止塌缩。

训练时应协调主任务与均衡目标。辅助系数过大可能为追求均匀而损害建模，过小则可能难以改变负载。有些模型用无辅助均衡损失的路由偏置调节等机制，不能直接用这里的公式解释它们；“没有均衡辅助损失”也不代表整个模型训练没有其他辅助目标。

## 7. 参数量、激活参数与实际成本

每个小专家有 $2DF=144$ 个参数，Router 有 $DE+E=28$ 个，四个路由专家加一个共享专家共有：

$$
P_{\mathrm{total}}=(DE+E)+(E+1)2DF=748.
$$

每个 Token 的路由专家只执行两个，按当前结构做一个激活参数代理统计：

$$
P_{\mathrm{active}}=(DE+E)+(K+1)2DF=460.
$$

这里把完整 Router 和共享专家计算都算进去，不能把 748 简单乘 $K/E$。这个“激活参数”也不是 FLOPs、显存或运行时间：权重可能被多个 Token 复用，优化器仍需维护总参数的状态，路由排序、索引与重排有额外开销，缓存、激活和通信另有预算。

当前批次实际调用过的专家集合还可能包含全部四个专家，所以“每 Token 激活两个专家”和“整个 batch 只需存两个专家”是两回事。若把 MoE 与 Dense 对照，需要先说明匹配总参数、每 Token 计算、训练 Token、时长还是部署约束；这些通常不能同时严格匹配。

在本仓库配套的 Python 3.12、PyTorch 2.8.0+cpu 环境中，seed 42 快速模式实际通过 71 项检查。容量前计数是 `[11,5,4,12]`；dropless 接受 32 条分配；容量为 1 时每个专家接受一条，丢弃 28 条；容量为 0 时丢弃全部 32 条。快路径与参考路径最大前向误差约为 $2.22\times10^{-16}$，参数梯度最大误差约为 $9.99\times10^{-16}$。

常规模式、快速 seed 7 也通过同样的检查集合。不同种子的负载和训练结果会变化；容差与通过数量应以实际运行报告为准，不要求所有机器输出逐位相同的小数。

## 9. 实际优化：一个有明确边界的小回归任务

正确性通过后，实验重新初始化一个 MoE，生成固定输入与合成目标：

$$
y=0.6xA+0.3\tanh(xB).
$$

$A,B$ 是固定随机矩阵；目标不是由专家编号直接产生，因此没有预设“某个专家必须学习某类 Token”。优化器为 AdamW，学习率 0.025，weight decay 为零。目标是 MSE 加 $0.01L_{\mathrm{bal}}$，全批量训练；没有文档、Tokenizer 或注意力层。

快速模式使用 40 个样本训练 80 步，常规模式使用 80 个样本训练 160 步。改变模式会改变随机数消费顺序和具体目标，不能把两个 MSE 直接当成同一任务的学习曲线。在 seed 42 的实际运行中：

| 模式 | 初始训练 MSE | 最终训练 MSE |
| --- | --- | --- |
| quick | 0.483297 | 0.000555 |
| standard | 0.484842 | 0.000454 |

快速模式最终容量前负载为 `[21,20,19,20]`，说明这次训练的选中分配较接近均匀；它并不证明专家形成了可解释分工。程序检查训练梯度和预测有限，以及训练 MSE 至少下降到初始值的一半。没有断言必须优于 Dense，也没有把均匀分配当成主任务成功。

这是训练集拟合，不包含独立验证集，更不是语言任务。要研究泛化，应另行生成验证输入并固定同一个目标函数；要研究稀疏计算收益，应增加合适的 Dense 对照并匹配预算。仅凭当前结果不能声称 MoE 改善了模型能力、参数效率或推理吞吐。

## 10. 专家并行为什么是另一个层次的问题

单机教学实现把所有专家参数放在同一进程，用索引完成本地分派。专家并行则把专家放到不同设备：Token 表示需要发送到专家所在设备，计算完成后还要还原位置并聚合。这通常涉及 All-to-All、跨设备 buffer、分块流水和通信与计算重叠。

此时最忙的专家、设备间负载差异、网络带宽与同步都可能影响批次时间。相同 Token 可以请求不同设备上的多个专家；容量还需说明是本地、全局还是某个并行组的统计。路由优化既要考虑模型目标，也要考虑系统瓶颈，单个矩阵乘法的加速未必能减少端到端时间。

本实验没有分布式通信、专家并行、融合 dispatch 内核或低精度量化。CPU 的 `elapsed_seconds` 只记录当前脚本的总运行范围，不能当作 GPU MoE 吞吐。后续阅读系统论文时，可把本章逐 Token 参考保留为小规模正确性基准，再单独研究分布式布局与性能。

## 常见错误与排查顺序

| 表现 | 首先检查 |
| --- | --- |
| 形状正确但输出不一致 | scatter 是否覆盖而非累加，权重是否与 Token 和槽对应 |
| Router 几乎没有主任务梯度 | 是否采用 Top-1 后归一化为 1，是否意外 detach 了权重 |
| 总负载不等于 $NK$ | 统计的是分配还是 Token，是否误把共享专家算入路由计数 |
| 容量后结果偏大 | 丢弃后是否意外重新归一化，与参考约定是否一致 |
| 空闲专家没有梯度 | 该批次是否真的给它分配过 Token，容量是否全丢弃 |
| 辅助项接近参考值却仍溢出 | 同时看硬计数、概率、容量和设备分布，不能只看单个标量 |
| 小例子正确但运行很慢 | Python 循环、动态小矩阵、索引与通信成本是否占主导 |

排查时先固定输入与参数，检查无容量前向，再检查全部梯度，最后加入容量与训练。不要同时更换路由公式、专家激活、容量策略和优化器，否则即使结果改变也很难判断原因。

## 练习与提示

1. **手算两个专家的聚合。** 某 Token 的选中分数是 `[0,log(3)]`，专家输出分别为 `[2,0]`、`[0,4]`，共享输出为 `[1,1]`。求最终输出。提示：权重是 $1/4,3/4$；先逐项乘权，再加共享路径。
2. **改变容量后的语义。** 增加“丢弃后对剩余请求重新归一化”的实现，同时修改逐 Token 参考。提示：两个请求都丢弃时分母为零，需要显式定义结果，而不是直接除法。
3. **检查 Top-1 梯度。** 把 $K$ 改为 1，分别比较主任务、均衡项、两者之和对 Router 的梯度。提示：使用 `autograd.grad` 或独立前向，避免混入此前累积的梯度。
4. **验证集与目标固定。** 为合成回归加入独立验证输入，保持 $A,B$ 相同，在多个种子下记录训练与验证 MSE。提示：目标矩阵不是模型参数，不应在验证时重新采样。
5. **提出公平的 Dense 对照。** 设计一个与每 Token FFN 参数代理接近的 Dense 网络，再记录总参数、实际训练预算和误差。提示：加入共享专家后，不应只根据 $K/E$ 缩放预算。
6. **改成容量因子。** 明确采用 $C=\lceil\alpha NK/E\rceil$，扫描不同 $\alpha$，报告容量前负载、接受量、丢弃分配率和主任务误差。提示：比例的分母是 $NK$，不要把它误写成 Token 丢弃率。

完成本章后，应能解释一个 Token 为什么去了某些专家、如何恢复原位置、哪些梯度来自连续权重，以及容量改变了什么。下一章将把这些局部规则与真实模型的配置和源码对应起来。
