# 13 独立架构实验：从假设到有边界的结论

最终项目不是把所有新模块拼在一起，而是对一个清楚的问题给出可信的回答。

## 先写一个可被推翻的假设

示例：固定 Query 头数、隐藏维度、数据与训练 Token，把 MHA 改为 GQA，预计 KV Cache 按 KV 头数比例下降；验证 loss 和实际 Decode 延迟的变化需要测量。

把理论可推导的部分与实验未知的部分分开。若数据不支持假设，保留失败分析，不删掉不理想的结果。

## 一个最小项目范围

1. 固定一个已经通过正确性检查的 Dense 基线。
2. 选择一个主要改动，例如 KV 头数、FFN 形式或局部注意力层比例。
3. 声明主要预算：Token、计算、墙钟时间或推理约束。
4. 先短跑筛选；有明确趋势时再增加预算与随机种子。
5. 同时记录能力、计算与内存成本。

## 报告模板

```text
研究问题与预期
基线、代码版本、数据与模型配置
预算约束和无法完全控制的变量
正确性检查与实现差异
训练结果与随机性
性能、显存及完整测量条件
异常、失败与替代解释
结论的适用范围
下一步最值得验证的假设
```

## 如何写结论

合适的结论应包含条件，例如“在本次模型规模、Tokenizer、长度和 Token 预算下观察到……”。不要只凭单次微型实验写“这个架构优于另一个架构”。没有显著差异也是结果，应检查统计波动、训练是否充分以及指标是否敏感。

## 后续专题

完成主线后，可选择 MLA 完整实现、MTP、递归／线性注意力、量化、Triton、并行训练或规模规律。每个专题仍沿用先解释、再验证、后测量的流程，而不是以收集组件名称作为学习目标。

## 结业验收

另一位开发者能够依据你的配置、代码版本与说明重跑核心实验，并理解结论成立的条件。研究成果可以是改进，也可以是对某个看似有效想法的可靠否定。
