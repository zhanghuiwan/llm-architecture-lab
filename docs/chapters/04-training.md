# 04 建立可信的训练基线

上一章把语言模型组装起来，并看到训练损失下降。本章暂时不增加结构模块，而是回答更基础的问题：这条训练曲线能否被解释、重跑，以及在中断后继续？如果不同结构实际看到了不同的数据、使用了不同的有效 Token 数，或者其中一次恢复时丢失了优化器状态，最后的 loss 差异就不能直接归因于结构。

本章的产物是一份可以检查的训练记录、一份可以恢复的检查点，以及一个关于梯度累积的数值对照。我们使用很小的 CPU 模型，把随机采样、Dropout、AdamW、学习率调度和梯度裁剪真正放进训练循环。模型刻意没有注意力层：它只根据当前位置的字符预测下一个字符，因此足以暴露训练流程错误，却不能替代上一章的 GPT，也不能用于评估长程语言理解。

## 学习目标与先修知识

读完并运行实验后，你应能做到：

- 区分训练样本数、输入 Token 数、参与损失的有效 Token 数与优化器更新次数。
- 在生成重叠训练窗口之前划分原始文档，解释随机划分窗口为什么可能泄漏。
- 写出长度不同、包含 padding 时的梯度累积权重，并通过整批梯度验证。
- 说明 AdamW 的历史状态、调度器状态和随机数状态为什么都影响恢复结果。
- 从真实轨迹判断“继续运行”和“从同样权重重新训练”的差别。

需要先掌握第 01 章的移位标签与交叉熵，以及第 03 章的 `forward → backward → optimizer.step`。本章用到的 `state_dict` 是对象状态的字典表示；它不是“整个实验”的自动快照。无需 GPU、外部数据集或预训练权重。

## 1. 先定义比较对象，再固定训练配方

“新结构比基线好”至少包含三个需要单独说明的判断：模型定义是否只改变了预定因素，训练资源是否可比，指标差异是否超出了数据与随机种子的波动。不要先跑出好看的曲线，再补一个与它不匹配的基线。

为一次实验写下以下记录。没有使用的功能明确写“未使用”，比省略后让人猜测更有用。

| 类别 | 需要记录的内容 | 为什么影响解释 |
| --- | --- | --- |
| 模型 | 配置、参数量、权重绑定规则、源码提交 | 改一个维度可能同时改变容量与计算量 |
| 数据 | 来源、许可、原始文档划分、去重、顺序 | 相似文本跨集合会使验证结果偏乐观 |
| 编码 | Tokenizer 版本、特殊符号、截断和拼接 | 同一段文本的预测位置可能发生变化 |
| 预算 | 更新次数、有效 Token、序列长度、批量 | 相同步数不一定消耗相同数据量 |
| 优化 | AdamW 参数、学习率曲线、衰减、裁剪 | 优化配方本身就能改变曲线 |
| 数值 | dtype、设备、混合精度设置 | 精度与算子实现影响数值和性能 |
| 测量 | 评估频率、固定验证集、指标聚合方式 | 改变采样范围会制造指标变化 |
| 恢复 | 检查点位置、恢复状态、已完成更新数 | 恢复遗漏会改变后续轨迹 |
| 随机性 | Python、框架、数据加载器等种子和状态 | 一个种子不涵盖所有随机来源 |

本章脚本报告使用的 seed、步数、有效 Token 数、每步实际学习率、输入批次哈希、训练损失与梯度范数。若用于正式比较，还应把执行命令、依赖版本和 `git rev-parse HEAD` 的结果连同 JSON 保存到实验记录中。脚本不会为了收集版本信息而修改仓库。

## 2. 数据边界必须早于重叠窗口

设一个原始文档包含字符序列 `abcdefgh`，窗口长度为 4，滑动步长为 1。得到的窗口包括 `abcd`、`bcde`、`cdef`。如果先生成窗口，再把窗口随机分到训练与验证，验证窗口中的大部分内容可能已经以几乎相同的上下文出现在训练中。这不是随机种子能修复的问题，而是样本边界定义错误。

推荐顺序是：确认数据来源与许可，按文档或业务上合理的实体分组，执行需要的去重和时间切分，固定训练/验证/测试清单，最后在各自集合内生成窗口。书籍、同一用户的对话、同一代码项目等存在强关联时，仅按文件随机划分也可能不够。

本实验内置两份训练短文和一份验证短文。训练文档反复描述“春风吹过山谷”“秋雨落在河边”，验证文档重新组合字符，形成不同的相邻关系。字符表是代码中预先固定的字母表，没有从验证集学习合并规则或频率。这个例子主要展示“训练 loss 下降不意味着验证 loss 同时下降”，并不代表真实语言建模数据集的分布。

脚本先分别调用 `windows(train_docs)` 与 `windows(validation_docs)`。每个窗口含 6 个字符 ID，随后使用：

```python
inputs = batch[:, :-1]   # [B, 5]
targets = batch[:, 1:]   # [B, 5]
```

一次更新取 4 个窗口，因此参与损失的有效位置为 `4 × 5 = 20`。这是预测目标数；不是窗口中的全部 24 个字符，也不是词数。实验中窗口全部等长且没有 padding，才能直接用这个乘积统计训练预算。

## 3. 从有效 Token 定义损失与预算

设一个批次有位置集合，位置损失为 $\ell_i$，是否参与损失的标记为 $m_i\in\{0,1\}$。正确的平均损失是：

$$
L=\frac{\sum_i m_i\ell_i}{N},\qquad N=\sum_i m_i.
$$

`ignore_index=-100` 常用于忽略 padding 标签，但不要把“被忽略的位置”与“模型完全没有看到的位置”混为一谈。`ignore_index` 控制损失，不会自动生成 attention mask，也不会自动防止一个有效位置关注 padding。带注意力的实现要分别处理两者。

整个训练过程的有效预算应按实际更新累加：

$$
N_{\mathrm{total}}=\sum_{u=1}^{U}\sum_{k=1}^{K_u}N_{u,k}.
$$

$u$ 是优化器更新，$k$ 是更新中的微批次。只有每个微批次都等长且完全有效，才可简化为 `更新数 × 微批次数 × 每批样本数 × 序列长度`。日志应说明使用的是实际读取位置数、有效目标数，还是去重后的 Token 数；它们解决不同问题，不能混用。

评估也应先汇总损失和与有效位置数，再相除。若直接平均一个长批次和一个短批次的平均 loss，就会人为提高短批次的影响。困惑度通常最后对全局平均的交叉熵取指数；先对每个批次取指数再平均，不是同一指标。

## 4. 梯度累积：累加总损失，统一除分母

内存不足时，可以把一个大批次拆成几个微批次，累加梯度后再更新。设第 $k$ 个微批次的有效 Token 数为 $N_k$，其平均 loss 为 $L_k$。整批目标是：

$$
L=\sum_k\frac{N_k}{\sum_jN_j}L_k.
$$

于是每个微批次应反向传播 `token_loss_sum / total_valid_tokens`，或者等价地对本地平均 loss 乘上有效 Token 比例。

```python
optimizer.zero_grad(set_to_none=True)
for microbatch in microbatches:
    logits = model(microbatch.inputs)
    loss_sum = cross_entropy(logits, microbatch.targets, reduction="sum")
    (loss_sum / total_valid_tokens).backward()
clip_grad_norm_(model.parameters(), max_norm)
optimizer.step()
```

这里的 `cross_entropy` 只是展示流程，实际脚本使用 `torch.nn.functional.cross_entropy`，并把 logits 的 `[B, T, V]` 展平为 `[B*T, V]`。若使用 `ignore_index`，`total_valid_tokens` 必须对应同一组目标。不能用序列张量的元素总数替代有效计数。

只有所有 $N_k$ 相等时，简单的 `loss / K` 才正确。脚本特意构造两个微批次：前一个有 10 个有效目标，后一个只有 2 个。正确权重分别为 $10/12$ 和 $2/12$；机械地各乘 $1/2$ 会把短微批次的相对影响放大三倍。

数值验证使用同一初始化的三份模型：整批一次反向、按有效 Token 加权累积、错误地平均微批次均值。它们关闭 Dropout，并使用 FP64，使差异尽量来自分母而非随机性。验证的是所有参数梯度的最大绝对差，而不是只比较两个看起来相近的 loss。

关闭 Dropout有一个重要目的：即使权重、输入和总分母相同，两个独立前向可能采到不同掩码。浮点加法的顺序也会影响末位。因而梯度累积的数学等价，不等于任意含随机算子的生产训练都能逐位复现。不能为了通过对照，临时关掉正式训练中的正则化后仍宣称正式配置已验证。

## 5. AdamW：状态不只是一组权重

普通 SGD 的最简更新只依赖当前梯度；Adam 类优化器还维护梯度的一阶和二阶滑动统计：

$$
m_t=\beta_1m_{t-1}+(1-\beta_1)g_t,\qquad
v_t=\beta_2v_{t-1}+(1-\beta_2)g_t^2.
$$

经过偏差修正后，更新大致由 $\hat m_t/(\sqrt{\hat v_t}+\epsilon)$ 决定。AdamW 把权重衰减与这个自适应梯度更新解耦。重新创建优化器而不加载状态，会重置历史矩和步数，即使模型权重、输入和当前学习率相同，下一次更新也会不同。

实验将矩阵参数放入 `weight_decay=0.01` 的组，偏置等一维参数放入不衰减组。这个分组是本实验明确选择的配方，不是所有架构通用的最佳规则。对真实 Transformer，embedding、norm 和特殊参数如何分组都应记录，不能只凭参数名字里是否含有某个子串猜测。

脚本中的反例从同一个检查点创建两份模型，恢复相同 RNG、相同学习率；其中一份恢复 Adam 状态，另一份使用新的优化器。两份模型在这一步更新前的 loss 必须相同，更新后的参数却应出现差异。这个对照把“前向没有变”与“优化轨迹改变”分开观察。

## 6. 学习率调度、清梯度与裁剪的顺序

本实验使用两步 warmup 加余弦衰减，并保留非零下限。调度器使用更新次数，而不是微批次数。一次正确顺序为：清梯度、计算 loss、反向传播、梯度裁剪、优化器更新、调度器更新。

```python
optimizer.zero_grad(set_to_none=True)
loss.backward()
norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 0.75)
lr_used = optimizer.param_groups[0]["lr"]
optimizer.step()
scheduler.step()
```

记录 `lr_used` 必须发生在 `optimizer.step()` 所用的时刻。如果记录的是调度器更新后的下一步学习率，曲线会平移，容易误判 warmup 行为。`LambdaLR` 在构造阶段也会应用初始系数，因此不要把配置里的基础学习率与第一步实际学习率默认视作同一个值。

`clip_grad_norm_` 返回的是裁剪前的总梯度范数，不是裁剪后的数值。脚本额外计算裁剪后的范数并检查不超过 `0.75`。梯度很小时不需要裁剪；不能据此判断函数失效。裁剪应在所有微批次累积完成后执行，否则会分别改变各部分梯度的方向组合。

`zero_grad(set_to_none=True)` 表示把梯度设为空，而不是逐元素写零。后续反向会重新产生梯度。无论采用哪种清零方式，都不要忘记它：未清理的梯度会跨优化器更新累积。使用混合精度时还需要先取消缩放，再按真实梯度裁剪；本章仅运行 FP64 CPU，不包含 scaler、CUDA 或混合精度验证。

## 7. 检查点保存的是恢复所需状态

一个最小但有意义的检查点包括：

```python
checkpoint = {
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "scheduler": scheduler.state_dict(),
    "cpu_rng": torch.get_rng_state(),
    "next_step": completed_updates,
    "total_steps": planned_updates,
    "data_sha256": data_hash,
}
```

这里的 `next_step` 是下一次应执行的更新编号；不要在保存后额外加一次更新，又把编号保持不变。调度函数需要使用与原实验相同的总步数重建，因为并非所有调度器都会把 Python 闭包中的参数序列化到状态字典。

`state_dict()` 返回的张量可能仍引用当前参数存储。如果只是把它留在内存字典里，继续训练可能让所谓的“中间快照”跟着变化。实验在保存时 `copy.deepcopy`，并通过临时文件真实执行 `torch.save` 与 `torch.load(..., weights_only=True)`。磁盘读写完成后再恢复，避免仅验证内存对象赋值。

实际项目还可能需要 Tokenizer/模型配置、数据迭代器位置、分布式采样器 epoch、Python `random` 和 NumPy RNG、各 CUDA 设备 RNG、混合精度 scaler、梯度累积中的进度等。本文没有使用这些随机来源或功能，不应声称已覆盖。若在累积尚未结束时保存，还必须恢复已经累积的梯度，或者明确只允许在完整更新边界保存。

不要加载来历不明的检查点。`weights_only=True` 缩小了加载允许的对象范围，并不构成对任何外部文件的完整安全认证。本章只读取脚本自己生成的临时文件，不下载或执行第三方对象。

## 8. 恢复随机数状态要放在正确位置

恢复流程的一个常见陷阱是：先设置 RNG，然后构造新模型。构造模型会随机初始化参数，已经推进了 RNG；之后虽然加载了旧权重，Dropout 与采样的随机位置仍发生偏移。

本实验采用以下顺序：

1. 按相同配置构造模型、优化器、调度器。
2. 加载模型状态、优化器状态、调度器状态。
3. 检查数据标识和训练位置。
4. 最后恢复 CPU RNG，再继续训练。

训练数据采样使用 `torch.randint`，模型中使用 `nn.Dropout(0.25)`，二者共享 CPU 默认生成器。因此恢复 RNG 不仅影响下一个批次，也影响 Dropout 掩码。脚本记录每个批次内容的 SHA-256，便于区分“数据顺序变了”和“输入相同但计算变了”。哈希相同不是一般意义上的无泄漏证明，只是这里的轨迹核对工具。

完整对照先连续运行全部更新，在中间点保存检查点；再从该点恢复，比较后续每一步的批次哈希、loss、学习率和范数，以及最终所有模型参数。本实验设置单线程、确定性算法、同一 CPU 环境和同一 dtype，要求轨迹与参数逐值相等。

这条结论范围很窄：同一实现、同一环境下的该实验可以精确恢复。换操作系统、框架版本、硬件、线程设置或分布式归约策略后，不应预期逐位相同。实际训练可以采用合理容差或统计复现目标，但必须提前声明；不能看到失败后随意放宽阈值。

### 应检查哪些 JSON 字段

`checks` 是断言结果，不是人工描述的“看起来正确”。核心检查包括恢复轨迹精确相等、最终参数逐值相等、遗漏 RNG 能被反例检测、丢失 Adam 矩改变更新、正确累积匹配整批梯度、错误累积产生差异。`metrics.trace` 保存连续训练轨迹，可以先核对恢复边界前后的批次哈希与学习率，再定位数值差异。

负向对照出现差异是预期行为；对应检查为 `true` 表示实验成功检测到错误，不表示错误实现本身正确。不要把 negative control 的 loss 或参数偏差并入正式模型的性能统计。

## 10. 常见故障与定位顺序

| 现象 | 优先检查 | 本章中的定位方式 |
| --- | --- | --- |
| 恢复后第一批数据就不同 | RNG、迭代器与采样器位置 | 比较批次 SHA-256 |
| 第一批和前向 loss 相同，更新后参数不同 | 优化器状态、学习率、裁剪顺序 | 对照丢失 Adam 矩的反例 |
| 学习率曲线整体错一格 | scheduler 调用与日志时机 | 查看每步实际使用的 LR |
| 累积 loss 看似相近但梯度不相等 | 有效 Token 分母、padding、随机层 | 关闭随机层后比较全部梯度 |
| 保存中间参数却变成最终参数 | 内存中的状态引用 | 深拷贝并进行真实文件读写 |
| 验证 loss 变差、训练 loss 变好 | 数据分布、过拟合、验证协议 | 固定探针、保留验证边界 |
| 多个 seed 结果相近 | 不代表已覆盖所有随机性 | 报告 seed 与实际覆盖范围 |

排查时一次改变一个因素。不要同时更换模型、数据、学习率和随机种子后，再推断某个因素是原因。先构造短、稳定、能失败的测试，比直接启动一场长训练更容易定位问题。

## 11. 练习与验收

**练习一：解释 10 与 2 的权重。** 手算两个微批次的正确比例，再把第二个微批次改为 5 个有效 Token。预期是错误等权平均仍不匹配，但差异具体大小取决于梯度；不要预先硬编码它必须变大或变小。

**练习二：新增一个梯度累积更新。** 把实验中的梯度对照扩展到一次 SGD 更新，检查最终参数仍在合理数值容差内相等。先保持 Dropout 关闭，再讨论开启后为何不能简单要求逐位一致。

**练习三：只恢复权重。** 分别故意遗漏 RNG、优化器和调度器状态，记录第一个产生差异的字段。提示：遗漏调度器不一定让恢复后的第一步 loss 变化，但会影响后续使用的学习率；必须观察跨步轨迹。

**练习四：改变验证分布。** 预先定义另一份与训练分布更接近但文档独立的验证集。固定选择规则并重新运行，解释两种验证集回答的问题有什么不同。不要反复查看验证结果后只保留较好的一份。

**练习五：设计一份真实训练恢复清单。** 如果训练包含多进程 DataLoader、梯度累积、CUDA 和混合精度，列出当前脚本尚未保存的状态。无需直接添加这些功能；先说明哪些可以重建、哪些必须序列化，以及在哪个边界保存最简单。

完成本章的标准不是会背一串优化器配置，而是能够拿出一次真实运行：数据划分清楚、有效预算可计算、累积分母正确、中断恢复经过对照、检查结果和适用范围都有记录。下一章再把数据管线扩展到 Tokenizer 与样本打包，届时这些训练约束仍然成立。
