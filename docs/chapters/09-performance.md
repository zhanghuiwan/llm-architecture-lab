# 09 性能测量与高效实现

前面的章节回答了“这个结构算得是否正确”。当公式已经固定，仍然可以有多种实现：显式生成注意力矩阵，调用一个融合接口，复用缓冲区，或者换一种张量布局。本章讨论怎样在保持语义的前提下比较这些实现。我们从一个很小的 CPU 实验开始，建立可以检查、可以复述的测量过程，再说明怎样把同样的方法扩展到 GPU 和服务端。

本章不会训练语言模型，也不下载权重。实验只使用随机 Q、K、V 张量，验证手工注意力与 PyTorch SDPA 的输出和梯度，再测量两个已经明确定义的前向工作负载。测量得到的是当前机器、当前版本与当前输入规模下的局部实现延迟，不能据此判断模型语言能力、完整推理服务的响应时间，或其他硬件上的优化收益。

## 学习目标与先修

你应当已经能读懂第 02 章的因果多头注意力，理解第 08 章的 Prefill、Decode 与缓存位置。完成本章后，应能做到：

- 对比两个实现之前，先检查输入、掩码、精度、dropout 和输出目标是否一致。
- 将数值正确性、理论工作量和实测时间分开记录，不用其中一种代替另一种。
- 写出包含预热、重复、计时范围和分位数的测量入口，解释为什么单次最快值不足以作结论。
- 区分完整序列 Prefill 与单步 Decode；说明局部注意力内核计时为什么不等于完整生成延迟。
- 识别 CPU 线程、GPU 异步、内存指标口径等常见误导，并明确哪些项目没有测量。

## 1. 先固定被比较的计算

本章所有注意力输入都按 `[B,H,L,d_h]` 组织，其中 B 是批量，H 是头数，L 是 Query 长度，$d_h$ 是头维度。Key、Value 为 `[B,H,S,d_h]`，S 是可供读取的 Key 长度。标准缩放点积注意力为：

$$
A=\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_h}}+M\right),\qquad O=AV.
$$

$QK^\top$ 的形状是 `[B,H,L,S]`。掩码 M 在允许位置为零，不允许位置为负无穷。每个 Query 必须至少有一个允许的 Key，否则显式 softmax 可能产生全屏蔽行的非法结果。本章所有样本没有 padding，使用相同头数和相同头维度，dropout 固定为零。

手工实现按公式分成三个步骤：矩阵乘、屏蔽后 softmax、加权求和。SDPA 分支使用 `torch.nn.functional.scaled_dot_product_attention`，传入相同的布尔允许掩码，`dropout_p=0.0`，`is_causal=False`。这里布尔值 True 表示允许参加注意力，不能直接套用其他接口中“True 表示屏蔽”的约定。选择显式掩码是为了让两个分支的可见范围直接对应，避免同时隐含两套因果规则。

```python
# allowed 可以广播到 [B,H,L,S]，True 表示可以读取。
scores = q @ k.transpose(-2, -1) / math.sqrt(q.shape[-1])
probabilities = scores.masked_fill(~allowed, -torch.inf).softmax(-1)
manual = probabilities @ v
reference = F.scaled_dot_product_attention(
    q, k, v, attn_mask=allowed, dropout_p=0.0, is_causal=False
)
```

注意 SDPA 默认已经包含标准缩放。不要在调用前把 Q 再除一次 $\sqrt{d_h}$，也不要让一个分支包含 dropout、另一个分支不包含。如果输入经过不同的投影权重、精度转换或归一化，即使最终张量形状一样，也不能把时间差归因于同一个注意力计算的实现优化。

SDPA 是接口，不是某一个内核的别名。实际后端由设备、dtype、形状、掩码和 PyTorch 版本等共同决定。调用成功不能证明使用了 CUDA FlashAttention；本章 CPU 结果也不能作为 FlashAttention 的速度测试。FlashAttention 类算法通过分块、融合和数据复用减少中间结果的高成本读写，并不等同于减少 KV 头数的 GQA，也不等同于限制可见范围的局部注意力。

## 2. 两个工作负载为何不同

### Prefill：完整提示序列

Prefill 分支设置 $L=S=T$。每个位置都产生 Query，同时只能读取自己及更早的 Key，允许矩阵是 `[T,T]` 的下三角。输出 `[B,H,T,d_h]` 一次覆盖全部位置。这仍然只是某一层的注意力子计算：没有输入 embedding、QKV 投影、输出投影、MLP、归一化或模型最后的词表投影。

真实 Decoder 的 Prefill 会通过所有层并填充缓存；本章不计缓存写入或内存分配策略。把这里的 `prefill` 名称理解为“Prefill 形状的注意力前向”，而不是完整模型的端到端 Prefill 延迟。

### Decode：一个新 Query 读取已有 KV

Decode 分支取完整 Q 的最后一行，设 $L=1,S=T$，使用与 Prefill 相同的 K、V。因为这个 Query 对应最后一个位置，所有 T 个 Key 都应可见。脚本传入 `[1,T]` 的全 True 掩码，并检查 Decode 输出等于完整 Prefill 输出的最后一行。

这里的 K、V 已包含当前位置，因此 S 表示本次读取的总长度。如果“历史长度”为 P，再追加当前 Token 的 K、V，则通常 $S=P+1$。实验没有实现缓存追加，也不包含复制缓存、分配缓存、查表或采样；这些过程可在第 08 章的完整解码路径中进一步测量。

非方阵因果掩码是一个很容易让基准变快却算错的位置。对于本章的 `L=1,S=T` 输入，直接用 SDPA 的 `is_causal=True` 会按接口的非方阵因果对齐规则处理，而不是自动知道这个 Query 的绝对位置是 $T-1$。实验加入一个错误分支，检查它与正确 Decode 输出确实不同。正确做法是根据 Query 和 Key 的绝对位置构造允许关系，或者在单个末尾 Query、无 padding 的受限场景下显式允许全部 Key。

如果为了让程序更快而少读取了一部分历史，或者错误地只读取首个 Key，虽然时间可能下降，但语义已经改变。正确性检查应当在任何计时之前执行，而不是等到得到漂亮的速度比后再补充。

## 3. 先验证前向与梯度

配套脚本首先使用 FP64，以减少舍入误差对参考对照的干扰。它用同一组 Q、K、V 分别计算手工结果与 SDPA 结果，记录最大绝对误差：

$$
\epsilon_O=\max_i |O_i^{\text{manual}}-O_i^{\text{sdpa}}|.
$$

输出接近还不够。训练时两个实现必须对输入产生相符的梯度。脚本生成同一个上游张量 U，将损失写成 $\langle U,O\rangle$，分别取得 Q、K、V 的梯度并比较：

$$
\epsilon_Q=\max_i|\nabla_{Q_i}\langle U,O^{\text{manual}}\rangle-
\nabla_{Q_i}\langle U,O^{\text{sdpa}}\rangle|.
$$

K 与 V 同理。这比只对 `output.sum()` 求导覆盖更多输出方向，但仍然是特定输入规模与种子的局部数值核对，不是所有输入上的数学证明。脚本还检查梯度有限、输出形状、Decode 与完整末尾位置的一致性，以及错误因果对齐的负向对照。

随后将输入转换为连续存储的 FP32，并再次核对两个实际计时分支的前向结果。FP64 检查使用 `1e-10` 的最大绝对误差阈值，FP32 前向使用 `1e-5`。阈值属于本章 CPU 小规模输入的验收条件，不是任意硬件、序列长度和低精度的通用标准。扩展到 BF16 或 FP16 时，应观察相对误差、绝对误差与任务影响，重新说明容差，不能只把断言删掉。

## 4. 理论工作量：有用，但不是秒表

将一次乘加计为两个 FLOPs，两个稠密矩阵乘的数量约为：

$$
F_{QK^\top}=2BHLSd_h,\qquad F_{AV}=2BHLSd_h,
$$

因此本章报告的 `dense_matmul_flops` 为 $4BHLSd_h$。它不包含 softmax、缩放、掩码、张量重排、投影和内存操作，也没有将因果上三角被屏蔽视为必然节省计算。手工稠密实现仍会先生成完整分数；优化内核可能跳过部分工作。这个数是清楚定义的稠密乘法参考预算，不是 profiler 测得的实际指令数。

Prefill 的 $L=S=T$，上述预算随 $T^2$ 增长。单步 Decode 的 $L=1,S=T$，预算随 T 线性增长。两者在同一个 B、H、T、$d_h$ 下的稠密乘法预算恰好相差 T 倍，但延迟不必相差 T 倍：CPU 调用成本、并行度、缓存命中、内存读取和内核选择也参与决定时间。

若每个元素占 e 字节，一个完整分数张量的大小为 $BHLSe$。K 与 V 的张量数据总量为：

$$
M_{KV}=2BHSd_he.
$$

快速实验使用 $B=2,H=4,T=32,d_h=16$、FP32，即 e=4。Prefill 的稠密矩阵乘参考预算为 524,288 FLOPs，一个分数张量为 32,768 字节；Decode 分别为 16,384 FLOPs 和 1,024 字节。两者使用同一份 KV，所以 KV 数据都为 32,768 字节。

“一个分数张量”不是完整临时内存峰值。显式实现可能同时保留分数、屏蔽后的张量和概率矩阵；训练还要保留反向状态。优化实现也有内部工作区。理论公式忽略对象开销、分配器缓存、对齐、模型参数以及运行时库，所以不能把这个字段标为进程峰值内存或显存实测值。脚本仅将 KV 公式与实际 K、V 的 `numel() * element_size()` 相加核对，保证数据字节口径一致。

## 5. 一个完整的计时过程

脚本固定 `torch.set_num_threads(1)`，所有随机输入、dtype 转换和 mask 创建都发生在计时之外。快速模式为每个分支预热 3 次，随后测量 9 轮，每轮连续调用 3 次；常规模式预热 8 次，测量 25 轮，每轮调用 5 次。

每轮用 `time.perf_counter_ns()` 读取开始和结束时间，再除以内层调用次数，得到一份平均每次调用的毫秒数。将多个调用放进一轮能减小计时器调用开销的相对影响，但不能消除 Python 循环和函数调用开销。这些开销属于本次测量口径，对非常小的张量可能占较大比例。

```python
with torch.no_grad():
    for _ in range(warmup):
        function()
    samples = []
    for _ in range(repeats):
        start = time.perf_counter_ns()
        for _ in range(inner_calls):
            function()
        samples.append((time.perf_counter_ns() - start) / inner_calls / 1e6)
```

`no_grad()` 的上下文在计时外建立，两种实现都不记录反向图。输出仍然实际计算并分配，不能把 Python 函数调用本身当成计算已经被消除。预热帮助排除首次调用、库初始化和一部分缓存冷启动效应，但不会保证机器进入固定频率或消除其他进程竞争。

报告保留每轮原始样本，而不是只保留一个平均数。median 是排序样本的中位数；p90 使用 nearest-rank 定义，即排序后的第 $\lceil0.9n\rceil$ 个样本。对于快速模式的 9 个样本，该定义会选择最大值；样本很少时，p90 自然粗糙。需要稳定尾延迟结论时，应增加重复次数并使用独立运行，而不是把快速检查的 p90 当成服务 SLA。

脚本记录最小值和最大值是为了帮助观察抖动，没有挑选最小值作为主要结果。`manual_over_sdpa_median_ratio` 等于手工 median 除以 SDPA median，大于一表示本次 SDPA median 较短，小于一则反过来。检查只要求样本为正且有限，不要求任何实现获胜。正确但较慢、或者两次测量结论反转，都应作为真实观察保留。

## 6. CPU、GPU 与内存口径

CPU 上的这些算子在本次函数返回前完成，可以用墙钟计时；线程数量、CPU 频率、NUMA 放置、后台负载和线程池设置仍会影响结果。本实验固定 PyTorch intra-op 线程数为一，并记录 Python、PyTorch、平台、机器架构与逻辑 CPU 数。逻辑 CPU 数不等于本进程可独占的核心数量；容器 CPU 配额、其他任务竞争等也不一定由这个数字体现。

GPU 的情况不同。CUDA 调用通常异步，如果只在 Python 侧包一个秒表，不做同步，读到的可能主要是任务提交时间。扩展 CUDA 测量时应使用 CUDA events 或在明确边界同步，并说明是在同一 stream 内测量设备时间，还是含主机调度的墙钟时间。同步本身也会改变流水线，不能一边追求端到端吞吐一边在每个细小算子后强制同步，再假装测到正常服务状态。

本章脚本只实现并执行 CPU 路径，`cuda_executed` 为 false，CUDA 峰值 allocated、reserved 以及 CPU 进程峰值字段均为 null。null 的含义是未测量，不是零，也不表示内存不重要。不要用 Python `tracemalloc` 的结果直接替代 PyTorch 原生张量存储和设备内存。

若以后测 GPU 内存，至少区分当前 allocated、峰值 allocated、reserved，以及来自驱动或其他库的额外占用。需要在相同准备阶段后重置峰值统计，避免把上一个候选方案的分配峰值带进下一个方案。缓存预分配、优化器状态和模型参数是否包含，也必须写入报告。不同口径的“峰值显存”不能直接放在一张排名表中比较。

在本章编写时的一次 Linux x86_64、PyTorch `2.8.0+cpu`、单线程快速运行中，FP64 Prefill 前向最大绝对误差为约 `6.66e-16`，Q/K/V 梯度最大误差分别约 `9.16e-16`、`1.47e-15`、`1.11e-15`。同次运行的注意力前向计时如下，单位为毫秒：

| 工作负载 | 手工 median | 手工 p90 | SDPA median | SDPA p90 |
| --- | ---: | ---: | ---: | ---: |
| Prefill | 0.0477 | 0.0641 | 0.0266 | 0.0390 |
| Decode | 0.0236 | 0.0351 | 0.0123 | 0.1012 |

这些是一次实际局部测量的例子，不是预期值或验收阈值。Decode 的 SDPA median 较低，但该次 p90 较高，说明只用一个中位数会掩盖抖动；9 轮样本不足以归因尾部波动。编写期间机器还运行其他工作，报告未控制 CPU 独占与频率。你应保留自己的原始样本，不能以是否接近本表判断程序正确。

同一实现、同一种子重复计时也不会得到相同时间。种子固定的是张量值，不是操作系统调度。要论证稳定收益，应在目标硬件上隔离负载、重复独立运行、扩大合适的工作负载，并记录差异是否超过测量噪声。常规模式改变了形状与重复次数，不能把它与快速模式的延迟直接相除，称为某种优化收益。

## 8. 从局部内核走向完整系统

本实验的 Decode 没有 QKV 投影、缓存追加、逐层循环、词表输出、采样、分词、网络传输或排队。真实单步生成时间还可能受到权重读取、KV 访问、批量组织和服务调度影响。把一个注意力内核快一倍，不能保证完整请求也快一倍；其他部分的占比决定总体收益上限。

同样，服务端 TTFT 可能包含请求排队、输入处理、Prefill、首个 Token 采样和传输，不等于本实验 `prefill` 字段。Token/s 也必须说明是单请求生成速度、批量聚合吞吐，还是训练的有效 Token 吞吐。延迟和吞吐可以有不同的最佳点，不能只报一个数字代表全部体验。

如果要扩展完整训练基准，应先确定是否包含前向、loss、反向、梯度同步、优化器、数据加载和主机到设备传输，再在同一口径下比较。若比较的是结构而非实现，参数量、有效 Token、精度和可见范围也要单独控制。有关预算选择见[统一实验规范](/experiments)，不要让一个速度测试悄悄变成训练量不同的能力比较。

## 常见问题与排查

| 现象 | 优先排查 |
| --- | --- |
| 前向误差很大但形状相同 | 缩放是否重复、mask 布尔语义、softmax 轴、QKV 投影或精度是否一致 |
| Prefill 对照通过，Decode 错误 | Query 的绝对位置、非方阵因果对齐、当前 Key 是否已包含、padding 范围 |
| FP64 通过，FP32 不通过 | 输入尺度、累积顺序、低精度容差与具体后端；不要先删除断言 |
| 多次运行速度比反转 | 张量太小、其他进程竞争、线程与频率、样本数量、首次调用和缓存效应 |
| GPU 墙钟时间异常短 | 操作是否异步、计时边界是否同步、是否只测到提交开销 |
| 内存看似为零或突然变大 | 指标是否真正采集、对象存活时间、预分配、分配器缓存与峰值重置 |

## 练习与提示

1. 将快速模式的 T 改为 64，先推导两个工作负载的稠密乘法 FLOPs、分数张量字节和 KV 字节变化，再实际运行。提示：Prefill 的分数张量随平方增长，单步 Decode 的分数和 KV 随线性增长；实测时间未必严格按该比例变化。
2. 把内层调用次数设为 1、3、10，保持输入和外层轮数相同，比较原始样本分布。提示：关注秒表与 Python 循环的相对开销，也要注意每轮变长可能改变调度与缓存状态。
3. 增加一个完整的 QKV 投影与输出投影基准，保留当前“仅注意力”的结果。提示：提前分配权重，说明是否计入投影，不要把两个范围不同的数字混成同一指标。
4. 将 Decode 的 Query 扩为多个末尾位置，自己构造绝对位置掩码。提示：不能把 `[1,T]` 的全 True 逻辑直接推广到整个分块；分块内后面的 Key 仍然属于前面 Query 的未来。
5. 设计一个 CPU 内存测量方案，但先写下要测张量数据、进程常驻集还是峰值。提示：三个口径不同，采样频率和进程复用也可能漏掉峰值；无法可靠测量时保留 null 比填入估算更诚实。
6. 如果你有 CUDA 环境，另建受控实验验证 FP32/BF16 数值和同步计时。提示：先读当前 PyTorch 后端限制，记录硬件、驱动与选择的接口，不因调用 SDPA 就宣称使用了某个特定内核。本章 CPU 验证不覆盖你的 CUDA 扩展。

## 完成本章的标准

你应能拿一份 JSON 报告，完整说明计算语义、输入形状、精度、设备、线程、计时范围、预热与重复方法，并区分观察到的时间差和有证据支持的稳定收益。能够指出未测量的内存和系统环节，比得到一个漂亮的倍数更有价值。进入下一章后，我们会改变可见范围研究长上下文，那属于结构与任务设计的变化，必须重新说明比较条件。
